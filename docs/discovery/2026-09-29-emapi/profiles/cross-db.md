Built 2026-09-29 by the lead data architect from the six unit profiles (`users.md`, `orders-funnel.md`, `orders-customer-catalog.md`, `orders-integrations.md`, `ecomweb-stores.md`, `emapi-stores.md`) plus new verification queries X1–X12 and, after critic review (revision 2, same day), X13–X24, and (revision 3, same day, 13:00–13:15 UTC) X25–X41 (appendix). All queries went through `atlasq.sh` (atlas EC2 over SSH → READ ONLY transaction on the Aurora read replica, PII-redacted output).

**Evidence labels (required on every claim).**
- **VALIDATED** = backed by a data query that was actually run (all such queries are in the users DB, the only readable one, or in a unit profile's SQL appendix). Sub-tags: **[exact]** full count/aggregate, **[profile]** figure from a unit profile's appendix.
- **STRUCTURAL** = inferred from schema / metadata / stats only (column types, constraints, `pg_class.reltuples` **[est]**, physical size, naming). Everything about orders, ecomweb and emapi is STRUCTURAL.
- **NEEDS-GRANT** = a hypothesis that needs data not currently readable; the exact table.columns are named, and consolidated in §8.
- **[inferred]** = reasoning on top of STRUCTURAL or VALIDATED facts; never a measurement.

**As-of stamps.** users-DB tables are live, so counts drift during the day. Key figures carry the query time; the revision-3 snapshot (X25, **2026-09-29 13:11 UTC**) is: `users_user` 996,283 (22,108 deleted, max id 1,411,173); `core_blacklisteduserdetail` 8,760 (ecom_users 7,088; 728 removed); `secondary_email_added_via_gift` 59,594; consumer log 5,113 (1,298 `in_progress`); producer log 14,150. **Tooling caveat.** The atlasq PII redactor rewrites ISO dates (`YYYY-MM-DD`, and raw `min/max(timestamp)`) as `<phone>`. All dates in this revision were produced with `to_char(ts, 'YYYY "m" MM "d" DD')` and are shown here as `YYYY-MM-DD`. Earlier date outputs that came back as `<phone>` were discarded, not guessed.

## 6. Registry implications (for `backend/app/atlas/definitions/`)

1. **User dimension = `ecom_users.users_user`, keyed on `username` (UUID).** Every other DB's user must be resolved to that UUID inside its own database, before any cross-DB join. Never join on a numeric user id or on `sub` across DBs. [VALIDATED on the users side (X5–X7, X17); cross-DB equality NEEDS-GRANT (V2)]
2. **Guest orders cannot be attributed to a person** across DBs. The 902 true-guest `guest_id` tokens most likely map to orders `users_guestuser.username` or `session_id`, and their emails to `users_guestuser.email` (V8, NEEDS-GRANT). Only `users_mergeduser` / `basket_mergedbasket` (orders) link a guest to a registered user. **Never use `is_guest` from blacklist rows as the registered/guest flag** (§1.3); test the reference against `users_user.username`. Note that orders also puts registered usernames into `guest_id` (396 events), so "has `guest_id`" is not a guest flag either. [VALIDATED, X30]
3. **Brand dimension = emapi `brands_brand.code`** (master, all channels). The order-side crosswalk goes through `catalogue_product.upc`, pending V3. Until then, brand-level order metrics must stay orders-local (`catalogue_product`), with provenance that says so. [STRUCTURAL]
4. **Offer dimension = `plusoffer.code`.** The one key verified by schema to be identical in orders, ecomweb and emapi. [STRUCTURAL]
5. **Revenue stays orders-local** (`order_orderlinequantitydetail.*_in_reporting_currency`) until youpay dedup and the youpay_db reconciliation (V5) run. [STRUCTURAL; NEEDS-GRANT to validate]
6. **Legacy dimension `user_legacy_state`** with values `linked` (57,754), `shell-created` (110,937; never logged in; 5,436 deleted), `native` (827,585) and the 3-user anomaly bucket, derived from `users_migratedtransactionlog` (`request_status` any true ⇔ legacy code attached) (§1.3b). Legacy tenure = `date_joined` where < 2023-05-09 (25,121 linked users); last legacy login = `last_login` (57,377 non-null, 99.95% before 2024) — both labelled "legacy platform", never current activity. Shell accounts must be excluded from "registered customers" denominators or reported separately. [VALIDATED, X34]
7. **Legacy crosswalk** (57,757 users with a code) resolves through `legacy_auth_code` → username (§1.3b). Any metric that spans the legacy platform needs this crosswalk as a registered dimension, not ad-hoc joins. [VALIDATED in users; cross-DB NEEDS-GRANT (V7)]
8. **Fraud/trust is a multi-DB concept.** `trusted_user` exists in 4 tables (users, orders profile, ecomweb, emapi) and `is_fraud` in 3 (emapi users_user, orders paymentdetail, orders youpay client). There are **two blacklist tables** (users 8,760 vs orders 48,646 est, §1.3c) that are not replicas. A registry "fraud status" metric must name its source table; do not union flags or blacklists until V9/V10 show they agree. Blacklist-volume metrics must split `ecom_users` into **rule-generated** (integration account, templated remark) and **analyst-entered** (human staff) and must net out un-blacklist events (395) and legacy removals (350). [VALIDATED for users (X26–X28, X35); STRUCTURAL for orders]
9. **Operational health metric: "unapplied blacklist requests (guest and registered)"** from `kafka_clients_blacklistuserconsumerdatalog` where `status='in_progress'`, reported as two counts: **guest (token) 902** — last seen 2025-05-12, not growing — and **registered (UUID in `guest_id`) 396** — 389 users, 18 blacklisted elsewhere, still arriving (58 in 2026). Probable cause: payload without `mark_as_fraud`/`reference_id` (0/1,298 vs 2,895/2,895 completed). Provenance: metric id, table, `status`, as-of timestamp. [VALIDATED, X30, X32]
10. **Channel dimension (recent)**: `users_cognitoissuedtokens.user_platform` → `app` (ios+android) / `web` / `unaccounted`, per user, with a "since" date (app from 2026-07-13, web from 2026-08-29). Use only as "recent login channel". [VALIDATED, X36]
11. The **grant request** (§8) must land before any cross-DB metric ships. Without hashed identity keys in orders, ecomweb and emapi the identity graph cannot be verified at all.
